# L2 - Detailed Requirements

**Source:** `docs/PRD-Stride-Link.pdf` and `docs/specs/L1.md`. Terms such as *run*, *init complete* and *belt active* are defined in L1.md.

**Conventions used throughout**

- Byte indices are zero-based. Byte 0 of every Echelon frame is `F0`; byte 1 is the frame type.
- Multi-byte values are big-endian (`hi` then `lo`).
- `ck` is the checksum: the sum of all preceding bytes, modulo 256.
- Frames are written as uppercase two-digit hex bytes separated by single spaces, for example `F0 A4 00 94`.
- Bluetooth identifiers (Observed, qdomyos-zwift `a23bb20`; the PRD abbreviates the service as `0bf669f1-…`):
  - Service: `0bf669f1-45f2-11e7-9598-0800200c9a66`
  - Write characteristic (`f2`): `0bf669f2-45f2-11e7-9598-0800200c9a66`
  - Notify characteristics (`f3`, `f4`): `0bf669f3-45f2-11e7-9598-0800200c9a66`, `0bf669f4-45f2-11e7-9598-0800200c9a66`
- Timing criteria are verified with a fake clock in Playwright. "Within *n* ms" means measured on the page's monotonic clock (`performance.now()`).

## L2-001: Single self-contained HTML file
**Traces to:** L1-001

The release artefact must be one file named `stride-link.html`, smaller than 200 KB (204,800 bytes). It must inline all scripts, styles, fonts and images, and must reference no external resource.

**Acceptance Criteria:**
1. Given a production build, when the build completes, then the output directory contains exactly one deliverable, `stride-link.html`, and its size is less than 204,800 bytes.
2. Given `stride-link.html`, when its markup is parsed, then it contains no `<script src>`, no `<link href>`, no `<img src>` and no CSS `url()` whose value is anything other than a `data:` URI.
3. Given a browser with all network access disabled, when `stride-link.html` is opened from disk, then the page renders completely with its intended fonts and styles.
4. Given the build pipeline, when the output reaches or exceeds 204,800 bytes, then the build fails with a message giving the actual size.

---

## L2-002: Connect available on supported browsers
**Traces to:** L1-001

Given a browser that exposes Web Bluetooth, the page must show an enabled **Connect** button and an ownership notice.

**Acceptance Criteria:**
1. Given Chrome or Edge with `navigator.bluetooth` defined and `getAvailability()` resolving `true`, when the page finishes loading, then a button labelled **Connect** is visible and enabled.
2. Given the page has loaded, when the tester views the area around Connect, then the text `Use Stride Link only on a treadmill you own.` is visible.
3. Given the page has loaded, when no button has been pressed, then no Web Bluetooth method other than `getAvailability()` has been called.

---

## L2-003: Unsupported browser message
**Traces to:** L1-001

When Web Bluetooth is missing, the page must say so in plain words and disable Connect.

**Acceptance Criteria:**
1. Given `navigator.bluetooth` is undefined, when the page loads, then the page shows exactly `This browser can't use Bluetooth. Open this file in Chrome or Edge.`
2. Given `navigator.bluetooth` is undefined, when the page loads, then the Connect button has the `disabled` attribute and pressing it does nothing.
3. Given `navigator.bluetooth` is undefined, when the page loads, then no exception reaches the console.

---

## L2-004: Bluetooth off or blocked
**Traces to:** L1-001

The page must explain why Bluetooth can't be used when the adapter is off, or when the browser blocks Bluetooth on a page opened from disk, and must point to the hosted copy.

**Acceptance Criteria:**
1. Given `navigator.bluetooth.getAvailability()` resolves `false`, when the page loads, then the page shows `Bluetooth is off or unavailable on this device. Turn it on to continue.` and Connect is disabled.
2. Given that state, when an `availabilitychanged` event reports `value: true`, then the message clears and Connect becomes enabled without a reload.
3. Given `requestDevice()` rejects with `SecurityError`, when Connect is pressed, then the page shows `This browser blocks Bluetooth on files opened from disk. Open the hosted copy instead.` followed by a link to the hosted HTTPS copy, whose URL is set at build time.
4. Given any of these messages is shown, when the tester presses Export log, then the export contains the error name and message.

---

## L2-005: Supported runtimes
**Traces to:** L1-001

Stride Link must support the current and previous stable major versions of Chrome and Edge on Windows, macOS, Linux, ChromeOS and Android.

**Acceptance Criteria:**
1. Given the Playwright suite, when it runs on the Chromium version bundled with the pinned Playwright release, then all acceptance tests pass.
2. Given the manual hardware checklist (L2-071), when a release candidate is tested, then the record lists the browser name, version and operating system of every run.
3. Given a browser outside the supported set that exposes `navigator.bluetooth`, when the page loads, then the page does not block it and behaves as specified for supported browsers.

## L2-006: Bluetooth chooser filters
**Traces to:** L1-002

Pressing Connect must open the browser chooser filtered to Strides by name prefix or Echelon service, with names starting `ECH` excluded. The chooser must open only from a Connect press.

**Acceptance Criteria:**
1. Given Connect is enabled, when the tester presses it, then `navigator.bluetooth.requestDevice` is called once with `filters` containing `{namePrefix: "STRIDE"}`, `{namePrefix: "Stride"}`, `{namePrefix: "stride"}` and `{services: ["0bf669f1-45f2-11e7-9598-0800200c9a66"]}`.
2. Given the same call, then `exclusionFilters` contains `{namePrefix: "ECH"}`, `{namePrefix: "Ech"}` and `{namePrefix: "ech"}`, and `optionalServices` contains the Echelon service UUID.
3. Given the page has loaded, when no Connect press has happened, then `requestDevice` and `getDevices` have not been called.
4. Given a run is in progress, when the tester views Connect, then it is disabled until the run ends.

---

## L2-007: Reject Echelon bikes after selection
**Traces to:** L1-002

A device whose name starts with `ECH` in any case must be rejected even if it reaches the page.

**Acceptance Criteria:**
1. Given the chooser returns a device named `ECH-SPORT-1234`, when the selection resolves, then no GATT connection is attempted and the page shows `This looks like an Echelon bike. Stride Link only tests Stride treadmills.`
2. Given the chooser returns a device named `echBike`, when the selection resolves, then the same rejection occurs.
3. Given a rejection, when it is shown, then Connect is enabled again and the rejection is logged with the device name.

---

## L2-008: Model variant detection
**Traces to:** L1-002

The system must choose the Stride 4 variant when the device name starts with `STRIDE4` in any case, and the standard variant otherwise.

**Acceptance Criteria:**
1. Given a device named `STRIDE4-ABC`, when it is selected, then the Stride 4 variant is used and the log records `Model variant: Stride 4`.
2. Given a device named `stride4x`, when it is selected, then the Stride 4 variant is used.
3. Given a device named `STRIDE-8S`, when it is selected, then the standard variant is used and the log records `Model variant: standard`.
4. Given a device with no name that matched on the service filter, when it is selected, then the standard variant is used and the page shows the name as `(unnamed device)`.
5. Given any selected device, when the run starts, then the page shows the device name and the variant.

---

## L2-009: Chooser cancelled
**Traces to:** L1-002

Cancelling the chooser must return the page to idle without an error state.

**Acceptance Criteria:**
1. Given the chooser is open, when the tester cancels it and `requestDevice` rejects with `NotFoundError`, then the page shows `No treadmill selected.` and Connect is enabled.
2. Given the cancellation, then no run is created and no verdict is shown.

---

## L2-010: GATT connection and service discovery
**Traces to:** L1-002

The system must connect, find the Echelon service and its `f2`, `f3` and `f4` characteristics within 10 seconds, and report each failure in plain words.

**Acceptance Criteria:**
1. Given a selected Stride, when connection succeeds, then the log records `Connected`, `Service found` and each characteristic UUID with its properties.
2. Given the device lacks the Echelon service, when discovery runs, then the page shows `This device doesn't expose the Echelon service. Is it a Stride?`, the device is disconnected and Connect is enabled.
3. Given connection and discovery together take longer than 10,000 ms, when the timeout elapses, then the page shows `Couldn't connect within 10 seconds. Move closer to the treadmill and try again.`, the attempt is abandoned and the device is disconnected.
4. Given any of these failures, when it occurs, then no frame has been written and the failure is logged with the error name and message.

---

## L2-011: Subscribe to both notify characteristics before any write
**Traces to:** L1-002

Notifications must be started on `f3` and `f4` before the first write, and each must be logged.

**Acceptance Criteria:**
1. Given the service is found, when subscription runs, then `startNotifications()` resolves on `f3` and on `f4` before the first `writeValue*` call on `f2`.
2. Given both subscriptions succeed, then the log contains `isNotifying f3: true` and `isNotifying f4: true`, each read from the characteristic's state after `startNotifications()` resolves.
3. Given `startNotifications()` rejects on either characteristic, when the failure occurs, then the page shows `Couldn't turn on treadmill notifications.`, no frame is written, the device is disconnected and the failure is logged.

---

## L2-012: Disconnect control and connection loss
**Traces to:** L1-002

The tester must be able to end a run, and the page must handle an unexpected disconnection cleanly.

**Acceptance Criteria:**
1. Given a run is connected, when the tester views the controls, then a **Disconnect** button is visible and enabled.
2. Given the tester presses Disconnect, when the belt is not active, then `gatt.disconnect()` is called and the page shows `Disconnected`.
3. Given a `gattserverdisconnected` event, when it fires, then all timers stop, the write queue is emptied, belt controls are hidden, the log records `Disconnected` with a timestamp, and Connect is enabled.
4. Given a disconnection, when it happens, then the log and verdict of the run are preserved.

---

## L2-013: Checksum
**Traces to:** L1-003

The checksum of a frame must be the sum of all preceding bytes modulo 256.

**Acceptance Criteria:**
1. Given bytes `F0 A4 00`, when the checksum is computed, then it is `94`.
2. Given bytes `F0 E0 FD 3E 65 48 D5`, when the checksum is computed, then it is `8D`.
3. Given bytes `F0 E0 34 12 05 78 97`, when the checksum is computed, then it is `2A`.
4. Given an inbound frame, when its last byte differs from the checksum of the bytes before it, then the parser marks it `checksumValid: false`.
5. Given an inbound frame shorter than 3 bytes, when it is checked, then it is marked `checksumValid: false` without throwing.

---

## L2-014: Outbound frame encoding
**Traces to:** L1-003

Every outbound frame must be built by the protocol module and must match these bytes exactly.

**Acceptance Criteria:**
1. Given the init frames, when encoded, then A4 is `F0 A4 00 94`, A1 is `F0 A1 00 91` and A3 is `F0 A3 00 93`.
2. Given the Stride 4 fixed init frame, when encoded, then it is `F0 E0 FD 3E 65 48 D5 8D`.
3. Given the activation or belt start command, when encoded, then it is `F0 B0 01 01 A2`; given belt stop, then it is `F0 B0 01 00 A1`.
4. Given the start-sequence frames, when encoded, then `D0 01 00` is `F0 D0 01 00 C1`, `D0 01 11` is `F0 D0 01 11 D2`, `A5 00` is `F0 A5 00 95` and `D3 02 01 F4` is `F0 D3 02 01 F4 BA`.
5. Given keepalive counter 1, when encoded, then it is `F0 A0 01 01 92`; given counter 255, then it is `F0 A0 01 FF 90`.
6. Given target speed 3.0 km/h, when encoded, then it is `F0 B2 02 0B B8 67`; given 1.5 km/h, then `F0 B2 02 05 DC 85`; given 0 km/h, then `F0 B2 02 00 00 A4`.
7. Given target incline 0, when encoded, then it is `F0 B1 01 00 A2`; given 5, then `F0 B1 01 05 A7`; given 15, then `F0 B1 01 0F B1`.
8. Given an unlock response for auth 57, when encoded, then it is `F0 E0 00 00 57 00 00 27`.

---

## L2-015: Inbound frame parsing
**Traces to:** L1-003

The parser must classify every inbound frame by type and must never throw, whatever bytes arrive.

**Acceptance Criteria:**
1. Given an inbound frame whose byte 0 is `F0`, when parsed, then its type is byte 1 (for example `D3`, `D2`, `D1`, `D0`, `E0`), and its checksum validity is reported.
2. Given an inbound frame whose byte 0 is not `F0`, or whose length is under 2, when parsed, then its type is `unknown`, it is logged, and it is neither decoded nor echoed.
3. Given a frame too short for its type's fields (D3 under 5 bytes, D2 under 4 bytes, D0 under 4 bytes), when parsed, then it is marked `malformed`, logged, and not decoded.
4. Given 10,000 random byte arrays of length 0 to 512, when each is parsed, then no exception is thrown and each returns a classification.
5. Given a zero-length `DataView`, when it is received as a notification, then it is logged as `RX (empty)` and processing continues.

---

## L2-016: Hex formatting
**Traces to:** L1-003

All frames shown on screen and in the export must use the same hex format.

**Acceptance Criteria:**
1. Given bytes `[0xF0, 0xA4, 0x00, 0x94]`, when formatted, then the result is `F0 A4 00 94`.
2. Given an empty byte array, when formatted, then the result is the empty string.
3. Given any byte from 0 to 255, when formatted, then it is two uppercase hex digits.

---

## L2-017: Standard variant init sequence
**Traces to:** L1-004

After subscription, the standard variant must write `A4`, `A1`, `A1`, `A1`, `A1`, `A3`, `A1` in that order. After each write resolves, the next frame must be written when a notification arrives or 300 ms elapse, whichever comes first.

**Acceptance Criteria:**
1. Given a standard-variant Stride with both subscriptions on, when init runs, then exactly 7 frames are written to `f2` in the order `F0 A4 00 94`, `F0 A1 00 91` (x4), `F0 A3 00 93`, `F0 A1 00 91`, each tagged `init`.
2. Given a fake treadmill that never notifies, when init runs, then each init write after the first starts 300 ms (+/- 20 ms) after the previous write resolved.
3. Given a fake treadmill that notifies 50 ms after each write, when init runs, then each next init write starts within 20 ms of that notification.
4. Given the last init write resolves, then the log records `Init complete`.

---

## L2-018: Stride 4 init sequence
**Traces to:** L1-004

The Stride 4 variant must write `A4`, `A4`, `E0 FD 3E 65 48 D5 8D`, `A4`, `A1` x4, `A3` with the same pacing as L2-017.

**Acceptance Criteria:**
1. Given a Stride 4 variant with both subscriptions on, when init runs, then exactly 9 frames are written in the order `F0 A4 00 94`, `F0 A4 00 94`, `F0 E0 FD 3E 65 48 D5 8D`, `F0 A4 00 94`, `F0 A1 00 91` (x4), `F0 A3 00 93`.
2. Given a fake that never notifies, when init runs, then pacing follows L2-017 criterion 2.
3. Given the Stride 4 fixed `E0` frame is written, then it is never treated as an inbound challenge.

---

## L2-019: Init write failure
**Traces to:** L1-004

A failed init write must be logged and must not stop the sequence.

**Acceptance Criteria:**
1. Given the third init write rejects with `NetworkError`, when the failure occurs, then the log records the frame hex, `write failed`, the error name and message.
2. Given that failure, then the sequence continues with the next frame after the 300 ms wait, and init still completes.
3. Given every init write fails, when init ends, then the run proceeds to verdict determination (L2-033 to L2-035).

---

## L2-020: Challenge recognition
**Traces to:** L1-005

An 8-byte inbound frame beginning `F0 E0` with a valid checksum, received while no acknowledgement is awaited, is an unlock challenge. Every inbound `E0` frame must be logged.

**Acceptance Criteria:**
1. Given notification `F0 E0 34 12 05 78 97 2A` on `f3` or `f4`, when no acknowledgement is awaited, then it is treated as a challenge and the log records `Challenge F0 E0 34 12 05 78 97 2A`.
2. Given notification `F0 E0 34 12 05 78 97 2B` (bad checksum), when no acknowledgement is awaited, then no response is written, the verdict is **Locked**, and the reason is `challenge checksum invalid`.
3. Given an inbound `F0 E0` frame of 7 or 9 bytes, when no acknowledgement is awaited, then no response is written, the verdict is **Locked**, and the reason is `challenge length 7` (or 9).
4. Given a challenge arrives during init, when it is received, then the unlock flow starts at once and init continues to completion in parallel through the write queue.

---

## L2-021: Unlock arithmetic
**Traces to:** L1-005

From challenge `F0 E0 b2 b3 b4 b5 b6 ck`, each byte is written as two uppercase hex digits. `a` is the leading run of decimal digits of hex(b4)+hex(b2), `b` is the leading run of hex(b3)+hex(b5), and `c` is the leading run of hex(b6), each read as a base-10 integer. auth = (a x b) mod c.

**Acceptance Criteria:**
1. Given challenge `F0 E0 34 12 05 78 97 2A`, when computed, then a = 534, b = 1278, c = 97 and auth = 57.
2. Given challenge `F0 E0 10 20 30 40 50 C0`, when computed, then a = 3010, b = 2040, c = 50 and auth = 0.
3. Given b4 = `3A` and b2 = `34`, when `a` is derived, then the digit string is `3A34` and a = 3.
4. Given b6 = `9A`, when `c` is derived, then c = 9.
5. Given any valid challenge, when auth is computed, then the log records a, b, c and auth in decimal.

---

## L2-022: Invalid challenge handling
**Traces to:** L1-005

A challenge that cannot produce a valid auth must end in **Locked** with a logged reason, and no response is written.

**Acceptance Criteria:**
1. Given challenge `F0 E0 34 12 05 78 00 93` (c = 0), when computed, then no response is written, the verdict is **Locked** and the reason is `zero divisor`.
2. Given challenge `F0 E0 34 12 A5 78 97 CA` (hex(b4)+hex(b2) = `A534`), when computed, then the verdict is **Locked** and the reason is `no decimal prefix in a`. Equivalent cases for `b` and `c` give `no decimal prefix in b` and `no decimal prefix in c`.
3. Given the auth validator receives a value above 99, when it validates, then it reports `auth out of range`. This guard is unit-tested directly because c is at most 99 from two hex digits.
4. Given any invalid challenge, when it is handled, then the reason appears on screen next to the verdict and in the log.

---

## L2-023: Unlock response and activation
**Traces to:** L1-005

For a valid challenge, the system must write `F0 E0 00 00 BCD(auth) 00 00 ck`, with the tens digit of auth in the high nibble, and then write activation `F0 B0 01 01 A2` 500 ms after the response write resolves.

**Acceptance Criteria:**
1. Given challenge `F0 E0 34 12 05 78 97 2A`, when it is received, then `F0 E0 00 00 57 00 00 27` is enqueued within 50 ms and tagged `unlock response`.
2. Given auth = 0, when the response is built, then it is `F0 E0 00 00 00 00 00 D0`.
3. Given the response write resolves, when 500 ms (+/- 20 ms) have elapsed, then `F0 B0 01 01 A2` is written and tagged `activation`.
4. Given an unlock attempt, when it completes, then the log contains the challenge hex, auth in decimal and the response hex.

---

## L2-024: Acknowledgement window
**Traces to:** L1-005

After the response write resolves, the system must wait 2,500 ms for an acknowledgement: an 8-byte `F0 E0` notification with a valid checksum whose byte 4 equals BCD(auth).

**Acceptance Criteria:**
1. Given auth = 57, when `F0 E0 00 00 57 00 00 27` arrives 2,400 ms after the response write resolved, then the verdict is **Unlocked** and the log records `Acknowledged`.
2. Given auth = 57, when no matching frame arrives within 2,500 ms, then the verdict is **Locked** and the reason is `no acknowledgement within 2.5 s`.
3. Given auth = 57, when `F0 E0 00 00 56 00 00 26` arrives inside the window, then it is logged as `E0 does not match auth`, the window stays open, and it is not treated as a new challenge.
4. Given an acknowledgement that arrives before the activation write, when it matches, then it counts and the activation is still written.

---

## L2-025: Repeated challenges
**Traces to:** L1-005

A new challenge received after an acknowledgement window has closed must start a new, numbered unlock attempt. The verdict reflects the latest attempt.

**Acceptance Criteria:**
1. Given attempt 1 ended **Locked**, when a new valid challenge arrives, then the log records `Unlock attempt 2` and the full flow of L2-021 to L2-024 runs again.
2. Given attempt 2 is acknowledged, when it completes, then the verdict changes to **Unlocked** and the log records `Verdict changed: locked -> unlocked`.

---

## L2-026: Counting keepalive
**Traces to:** L1-006

From init complete until disconnection, the system must write `F0 A0 01 n ck` every 2,000 ms. `n` starts at 1, counts to 255 and wraps to 1.

**Acceptance Criteria:**
1. Given init has completed, when 2,000 ms (+/- 50 ms) have elapsed, then `F0 A0 01 01 92` is written and tagged `keepalive`.
2. Given keepalives continue, when the 255th is written, then it is `F0 A0 01 FF 90`, and the 256th is `F0 A0 01 01 92`.
3. Given any keepalive, then `n` is never 0.
4. Given a disconnection, when it occurs, then no further keepalive is written.
5. Given init has not completed, then no keepalive is written.

---

## L2-027: Echo replies
**Traces to:** L1-006

Every inbound `D0`, `D2` and `D3` frame, from either notify characteristic, must be written back to `f2` byte-for-byte. This applies under every verdict and whether or not the checksum is valid.

**Acceptance Criteria:**
1. Given inbound `F0 D3 02 0B B8 88`, when it is received, then `F0 D3 02 0B B8 88` is enqueued within 50 ms, tagged `echo`.
2. Given inbound `F0 D2 01 05 C8` and `F0 D0 01 07 C8`, when they are received, then each is echoed unchanged.
3. Given inbound `D1`, `E0` or `unknown` frames, when they are received, then they are not echoed.
4. Given a **Silent** verdict already reached, when a late `D3` arrives, then it is still echoed.

---

## L2-028: Speed from D3
**Traces to:** L1-007

For a `D3` frame of at least 5 bytes, speed in km/h must equal ((byte 3 << 8) | byte 4) / 1000.

**Acceptance Criteria:**
1. Given `F0 D3 02 0B B8 88`, when decoded, then speed = 3.000 km/h and the page shows `3.00 km/h`.
2. Given `F0 D3 02 00 00 C5`, when decoded, then speed = 0 and the page shows `0.00 km/h`.
3. Given a `D3` frame of 4 bytes, when received, then speed is not updated and the frame is logged as `malformed`.

---

## L2-029: Speed from Stride 4 D1
**Traces to:** L1-007

For the Stride 4 variant only, a `D1` frame of at least 9 bytes must set speed in km/h to ((byte 7 << 8) | byte 8) / 100.

**Acceptance Criteria:**
1. Given the Stride 4 variant and `F0 D1 00 00 00 00 00 01 2C 00 00 48`, when decoded, then speed = 3.00 km/h.
2. Given the standard variant and the same frame, when decoded, then speed is not updated from it.

---

## L2-030: Incline from D2
**Traces to:** L1-007

For a `D2` frame of at least 4 bytes, incline must equal byte 3.

**Acceptance Criteria:**
1. Given `F0 D2 01 05 C8`, when decoded, then incline = 5 and the page shows `5`.
2. Given a `D2` frame of 3 bytes, when received, then incline is not updated and the frame is logged as `malformed`.

---

## L2-031: Heart rate from D1
**Traces to:** L1-007

For a `D1` frame of 12 bytes or more whose byte 11 is above 0, heart rate in bpm must equal byte 11. This applies to both variants.

**Acceptance Criteria:**
1. Given `F0 D1 00 00 00 00 00 01 2C 00 00 48`, when decoded, then heart rate = 72 and the page shows `72 bpm`.
2. Given a 12-byte `D1` frame whose byte 11 is `00`, when decoded, then heart rate is not updated.
3. Given an 11-byte `D1` frame, when decoded, then heart rate is not updated.

---

## L2-032: Telemetry display
**Traces to:** L1-007

Speed, incline and heart rate must each show the last decoded value with its unit, or a dash before the first value. Values must not be cleared for staleness, because the treadmill sends speed and incline only when they change.

**Acceptance Criteria:**
1. Given a new run, when no telemetry has been decoded, then speed, incline and heart rate each show `—`.
2. Given speed was decoded as 3.00 km/h, when 60 s pass with no `D3` or `D1`, then the page still shows `3.00 km/h`.
3. Given a telemetry frame is received, when it is decoded, then the displayed value updates within 100 ms.
4. Given a new run starts, when it begins, then all telemetry values reset to `—`.

---

## L2-033: Silent verdict
**Traces to:** L1-008

If no notification of any kind is received within 20,000 ms after init complete, the verdict must be **Silent**. Silent is final for the run.

**Acceptance Criteria:**
1. Given a fake treadmill that never notifies, when 19,900 ms have elapsed since init complete, then no verdict is shown.
2. Given the same fake, when 20,000 ms (+/- 50 ms) have elapsed, then the verdict is **Silent** with reason `no notification within 20 s of init`.
3. Given a **Silent** verdict, when a notification arrives later, then it is logged and handled per L2-027, and the verdict stays **Silent**.

---

## L2-034: Talks verdict
**Traces to:** L1-008

The verdict must be **Talks** when at least one notification has been received, none was an `E0` challenge, and 3,000 ms have passed since init complete. If the first notification arrives later than 3,000 ms but within 20,000 ms of init complete and is not a challenge, the verdict must be **Talks** at once. A later valid challenge must start the unlock flow and replace the verdict.

**Acceptance Criteria:**
1. Given a fake that sends `F0 D3 02 00 00 C5` during init and no `E0`, when 3,000 ms have elapsed since init complete, then the verdict is **Talks**.
2. Given a fake that sends its first notification, a `D2`, 8,000 ms after init complete, when it is received, then the verdict is **Talks**.
3. Given a fake that sends a `D3` during init and a valid challenge 1,000 ms after init complete, when 3,000 ms elapse, then the verdict is not **Talks**, and the unlock flow decides it.
4. Given a **Talks** verdict, when a valid challenge arrives, then the unlock flow runs and the log records `Verdict changed: talks -> unlocked` (or `-> locked`).

---

## L2-035: Verdict on disconnection
**Traces to:** L1-008

A disconnection after init has started but before a verdict must still produce one of the four verdicts.

**Acceptance Criteria:**
1. Given no notification has been received, when the device disconnects, then the verdict is **Silent** with reason `disconnected before any reply`.
2. Given notifications were received and no challenge, when the device disconnects, then the verdict is **Talks**.
3. Given an acknowledgement is awaited, when the device disconnects, then the verdict is **Locked** with reason `disconnected before acknowledgement`.
4. Given a verdict was already reached, when the device disconnects, then the verdict is unchanged.

---

## L2-036: Verdict presentation
**Traces to:** L1-008

The verdict must be shown as a word, with its meaning, its reason where one exists, and its next step, using the PRD's wording. Export log must be offered with every verdict.

**Acceptance Criteria:**
1. Given **Silent**, when shown, then the meaning reads `No notification within 20 s of init` and the next step reads `Export the log; capture the official app for comparison`.
2. Given **Talks**, when shown, then the meaning reads `Notifications arrive and no challenge was sent` and the next step reads `Read telemetry; belt commands can be tried`.
3. Given **Unlocked**, when shown, then the meaning reads `Challenge answered and acknowledged` and the next step reads `Read telemetry; belt commands can be tried`.
4. Given **Locked**, when shown, then the meaning reads `Challenge invalid or not acknowledged in 2.5 s`, the reason is shown, and the next step reads `Export the log with the challenge bytes`.
5. Given any verdict, when shown, then an **Export log** button is visible and enabled.
6. Given any verdict, when it is reached or changes, then it is announced through an `aria-live="polite"` region.

## L2-037: Frame and event capture
**Traces to:** L1-009

Every frame written or received, and every protocol event, must be recorded in order with a monotonic timestamp.

**Acceptance Criteria:**
1. Given a run, when any frame is written to `f2`, then a `TX` entry is recorded with timestamp, `f2`, hex and tag (`init`, `unlock response`, `activation`, `keepalive`, `echo` or `belt`), whether or not the write succeeded. A failed write adds the error.
2. Given a run, when any notification is received, then an `RX` entry is recorded with timestamp, the source characteristic (`f3` or `f4`), and hex.
3. Given a run, when an event occurs (connect, subscription state, model variant, init complete, unlock values, verdict, verdict change, error, disconnect), then an `EV` entry is recorded.
4. Given any two consecutive entries, then the later timestamp is greater than or equal to the earlier one.
5. Given a fake treadmill that exchanges *N* frames, when the run ends, then the log has exactly *N* `TX` and `RX` entries.

## L2-038: Log line format
**Traces to:** L1-009

Each log line must use one fixed, diff-friendly format: `<ms> <DIR> <char> <hex> <tag>`. `<ms>` is milliseconds since the run started, with one decimal place, right-aligned to 10 characters.

**Acceptance Criteria:**
1. Given the first init write at 12.34 ms, when it is logged, then the line is `      12.3 TX f2 F0 A4 00 94 init`.
2. Given a notification on `f4`, when it is logged, then the line has the form `<ms> RX f4 <hex>`.
3. Given an event, when it is logged, then the line has the form `<ms> EV <text>`.

## L2-040: Export log
**Traces to:** L1-009

Pressing **Export log** must download a UTF-8 `.txt` file, generated locally, containing a header, every entry of every run on the page, and each run's verdict.

**Acceptance Criteria:**
1. Given the log has at least one entry, when Export log is pressed, then a file named `stride-link-<device>-<YYYYMMDD-HHMMSS>.txt` downloads. `<device>` is the device name with every character outside `[A-Za-z0-9_-]` replaced by `_`, or `unknown`.
2. Given the export, when it is read, then its header contains the Stride Link version and build commit, `navigator.userAgent`, `navigator.userAgentData` brands and platform where available, and the run start time in ISO 8601.
3. Given each run in the export, then it has a `Run <n>` heading, the device name, the model variant, every entry in the L2-038 format, and a closing `Verdict: <word>` line with its reason, or `Verdict: none` if the run ended before init.
4. Given the export, when it is generated, then no network request is made. It is built from a `Blob` and an object URL that is revoked after the download starts.
5. Given the export, then lines end with LF and the file has no byte-order mark.
6. Given an error before any verdict (for example L2-010 criterion 2), when Export log is pressed, then the export contains that error.
