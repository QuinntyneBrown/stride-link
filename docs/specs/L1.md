# L1 - High-Level Requirements

**Product:** Stride Link, a standalone Echelon Stride connectivity smoke test
**Source:** `docs/PRD-Stride-Link.pdf` (Nov 20, 2026). PRD requirement IDs (SL-01 to SL-09) are cited as **Source** on each L1.
**Protocol basis:** qdomyos-zwift at commit `a23bb20`. All protocol facts are **Observed**, not confirmed on a Stride.

**Out of scope (PRD non-goals):** workouts, sessions, progress, classes and video; the Echelon bike; the virtual-Echelon proxy; iOS and Safari; any backend, analytics or network request.

**Terms used in L1 and L2**

| Term | Meaning |
|---|---|
| Run | One connection to one treadmill, from pressing **Connect** to disconnection. |
| Verdict | The outcome of a run. It is exactly one of **Silent**, **Talks**, **Unlocked** or **Locked**. |
| Standard variant | Any Stride whose name does not start with `STRIDE4`. |
| Stride 4 variant | A Stride whose name starts with `STRIDE4` (any case). |
| Init complete | The moment the write of the last init frame resolves. |
| Belt active | True while Start has been pressed and no Stop write has succeeded since, or while the latest decoded speed is above 0. |
| Frame | One byte array written to (TX) or notified by (RX) the treadmill. |

---

## L1-001: Single-file delivery and browser support
**Source:** SL-01, Platform and distribution

Stride Link must ship as one self-contained HTML file that a tester downloads and opens in Chrome or Edge on desktop or Android, with no install, no account and no network access. The page must tell the tester plainly when their browser or device cannot use Bluetooth.

## L1-002: Treadmill discovery and connection
**Source:** SL-02, SL-03

The system must let the tester pick an Echelon Stride from the browser's Bluetooth chooser, reject Echelon bikes, detect the Stride 4 variant, connect to the Echelon service, and subscribe to both notification characteristics before it writes anything.

## L1-003: Echelon frame codec
**Source:** Protocol reference, Frames table

The system must encode every outbound Echelon frame byte-exactly, compute and verify checksums, and parse every inbound frame safely, treating all bytes from the treadmill as untrusted input.

## L1-004: Init handshake
**Source:** SL-04

The system must run the qdomyos-zwift init sequence for the detected variant, in order, pacing each frame on the treadmill's reply or a short timeout.

## L1-005: Direct challenge/response unlock
**Source:** SL-05, Unlock arithmetic

When the treadmill sends an unlock challenge, the system must compute the response locally, write it, write the activation frame, and determine from the acknowledgement whether the treadmill unlocked.

## L1-006: Link maintenance
**Source:** SL-06

While connected, the system must keep the link alive with a counting keepalive and must echo back every speed, incline and unknown D0 notification, as qdomyos-zwift does.

## L1-007: Telemetry decoding and display
**Source:** SL-07

Once the treadmill talks, the system must decode and show speed, incline and heart rate from the frames each variant sends.

## L1-008: Verdict determination and presentation
**Source:** SL-07, SL-09, connection flow

Every run that reaches init must end in exactly one of four verdicts (Silent, Talks, Unlocked, Locked), shown in words with its meaning, its reason and the next step.

## L1-009: Packet log and export
**Source:** SL-03, SL-05, SL-09, Goal 4

The system must record every frame sent and received, and every protocol event, with a monotonic timestamp, and let the tester export the full log as a plain-text file that is enough to reproduce the verdict and to diff against a capture of the official app.

## L1-010: Opt-in belt control with safety interlocks
**Source:** SL-08, Safety

Belt commands must stay unavailable until the tester confirms they are standing clear. Speed must be capped at 3 km/h, and a Stop control must always be on screen and reachable by keyboard while the belt is active.

## L1-011: Privacy and security
**Source:** SL-09, Privacy, Risks

Nothing shall leave the device. The page must make no network requests, must enforce a Content Security Policy that allows nothing off-origin, must render all device-supplied and error text as text, never as HTML, and must persist nothing between page loads.

## L1-012: Performance and reliability
**Source:** Goals 1-3, Success measures

The page must load fast, keep protocol timing within stated tolerances, serialise all Bluetooth writes, stay responsive through long sessions, and handle every failure and disconnection without losing the log.

## L1-013: Accessibility
**Source:** Accessibility

The page must be fully operable by keyboard and touch, meet WCAG 2.2 AA, use 44 x 44 px minimum targets, and never convey a verdict or state by colour alone.

## L1-014: Responsive layout
**Source:** Runtime (desktop or Android)

The page must work at every viewport size, from extra small (phone, under 576 px) to extra large (1200 px and up), in portrait and landscape.

## L1-015: Build, test and release engineering
**Source:** Code, Tests, Distribution, Safety

The system must be written in TypeScript, keep the protocol in a pure, unit-tested module, verify every verdict with Playwright against a fake `navigator.bluetooth`, release a verifiable artefact with its SHA-256, and keep hardware testing a manual, human-only activity.
