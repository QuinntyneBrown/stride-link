Theming

Light and dark from one token file, following the OS, with contrast and forced-colours modes.

Overview

Two themes from one token file. Light is the default; dark mirrors the logo sheet's reversed lockup (paper on ink). Themes override the semantic tier only; primitives never change and components never know which theme is on.

How themes apply

:root,
[data-theme="light"] { /* primitives + light semantic tokens */ color-scheme: light; }
[data-theme="dark"]  { /* dark semantic tokens */ color-scheme: dark; }
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) { /* the same dark block */ }
}
  • OS preference applies dark automatically unless the page forces light.
  • data-theme on <html> forces a theme; on any element it themes that subtree (the documentation's side-by-side specimens use this).
  • color-scheme is set per theme so native controls, scrollbars and the number input spinner follow.
  • The shipped product has no theme switch: it follows the OS preference only. The toggle on these pages and in the mocks is tooling.

Token tiers

TierPrefixChanges when
Primitive--palette-*, --font-*, sizesThe brand changes. Never themed.
Semantic--color-*, --text-*, --space-*, --radius-*, --shadow-*, --duration-*, --z-*, --layout-*What a role means changes. Themes override this tier.
Component--btn-*, --field-*, --panel-*, --verdict-*, --alert-*, --toast-*…One component's look changes. Declared in components.css, always aliasing a semantic token.

Preference modes

Media queryEffect
prefers-color-scheme: darkDark semantic tokens unless data-theme="light".
prefers-reduced-motion: reduceDurations become 0 ms; components remove all animation and transition (L2-063).
prefers-contrast: more--color-border-default becomes strong, muted text becomes default, subtle becomes muted.
forced-colors: activeFocus ring Highlight; borders and the mark's arcs CanvasText; buttons, inputs and badges get system borders and the primary button Highlight.

This file versus the shipped tokens

docs/design-system/tokens/tokens.css is src/styles/tokens.css with three changes:

#ChangeWhy
1@font-face URLs point at ../assets/fonts/Folder layout; the shipped build inlines the fonts as data URIs.
2Adds --color-info-icon-on-inverse, --color-success-icon-on-inverse, --color-warning-icon-on-inverse, --color-danger-icon-on-inverseToast icons on the dark theme's paper inverse surface were 1.5–1.9:1 with the plain icon tokens. Toasts are mocks only, so the shipped file does not need them yet.
3The light block's selector is :root, [data-theme="light"]Lets a light specimen sit inside a dark page. The shipped page never nests themes, so it does not need it.

Everything else, including the mocks' docs/mocks/assets/tokens.css, is identical value for value.

Adding a theme

  • Add a [data-theme="<name>"] block that overrides semantic colour tokens only.
  • Add the theme to every pair check: check_contrast.py reads every data-theme block.
  • Keep the two dark blocks (attribute and media query) identical; copy one into the other.
  • Re-export tokens.json.

tokens.json

tokens/tokens.json is the same tokens in the W3C Design Tokens (DTCG) format, generated from tokens.css: each token has $type and $value, aliases are written {palette.signal.500}, light values are the defaults and dark overrides sit under $extensions. Regenerate it after any change:

python3 .claude/skills/extracting-design-systems/scripts/tokens_to_json.py docs/design-system/tokens/tokens.css

Usage

  • Never write [data-theme="dark"] .my-component: if a component needs a different colour in dark, the semantic token is wrong or missing.
  • Never hard-code a colour in component CSS; the design-system checker rejects hex, rgb, hsl, white and black outside tokens/.
  • Dark is not inverted light: surfaces lighten as they rise, status backgrounds become deep tints with light text, danger labels flip to near-black.
